# 06 - 排错实录（bug 全记录）

按发现顺序记录，每条含症状→根因→修复。都是真实踩过的坑。

## 1. mpegts 推流 30 秒后电视自停

- **症状**：直推 mpegts 裸流，电视播 30 秒进入 PAUSED_PLAYBACK
- **根因**：乐播把 ts 当静态文件下载，拉完缓冲区即认为"文件结束"
- **修复**：改推 HLS——ffmpeg 切片 + `omit_endlist`（直播语义），电视无限刷新播放列表

## 2. ffmpeg https 源报 certificate verify failed

- **症状**：curl 拉同 URL 正常，ffmpeg 报 `error:0A000086:SSL routines::certificate verify failed`
- **根因**：自编译 ffmpeg 无系统 CA bundle
- **尝试失败**：`-tls_verify 0` → "Option not found"（不是输入选项，ffmpeg 直接退出）
- **修复**：国内源改用 http 明文（80 端口普遍开放）
- **2026-10 更新**：ffmpeg 改用系统 PATH 的 brew 版（自带 CA bundle）后，https 源可直接拉，本坑仅影响旧自编译版；`-timeout` 选项两版均支持

## 3. ffmpeg 输出文件已存在导致挂死

- **症状**：`File 'tv_buf.ts' already exists. Overwrite? [y/N] Not overwriting - exiting`
- **修复**：命令固定加 `-y`

## 4. Popen 管道写 HTTP 响应 0 字节

- **症状**：`subprocess.Popen(cmd, stdout=self.wfile)` 客户端收到 Content-Type 但 0 数据
- **根因**：组合问题（当时 `-tls_verify` 也在命令里导致 ffmpeg 秒退）
- **修复**：stderr 落日志文件排查出真实报错后逐项解决

## 5. 「Remote end closed connection without response」

- **症状**：Stop/Set/Play 偶发此错误
- **根因**：电视 SOAP 服务并发处理弱，前一个请求没结束又来新的
- **修复**：调用间 sleep；查询加 3 次重试

## 6. state 永远 UNKNOWN（最大坑）

- **症状**：播放正常，但 /api/status 的 state 一直是 UNKNOWN；手工跑同样代码却正常
- **排查路径**：
  1. 怀疑代理干扰 → 检查进程环境变量，干净，排除
  2. 怀疑并发限流 → 加重试，无效
  3. 怀疑 SSDP 地址错 → 对比正常
  4. **加临时 /api/debug 端点返回 SOAP 原始响应** → `nonnumeric port: 'AVTransport_control'` 破案
- **根因**：URLBase 拼接 controlURL 时没补斜杠，`http://x:49152_urn:...` 端口部分变成 `49152_urn`
- **修复**：`controlURL.startswith("/") ? 直接拼 : 补 "/"`
- **教训**：被吞掉的异常要用原始响应暴露，光看返回码不够

## 7. 兜底线程 UnboundLocalError

- **症状**：`UnboundLocalError: local variable 'st' referenced before assignment`（后台线程堆栈）
- **根因**：直连 SOAP 本身失败（非 200）时跳过整个 if 块，`st` 未定义就被日志引用
- **修复**：`st = None` 提到 if 之前
- **教训**：兜底路径恰恰在异常场景触发，其自身代码要最健壮

## 8. 旧进程杀不干净（两次！）

- **症状 A**：`kill 17836` 后 5555 监控循环还在跑 → zsh wrapper 拉起了循环体
- **症状 B**：`pkill -f "python3 tv.py"` 无效 → Xcode Python 进程命令行是 `Python tv.py`（大小写/路径不同）
- **修复**：`pkill -9 -f "tv.py"`（宽松匹配）+ `lsof -ti :8899 | xargs kill -9`（按端口兜底）
- **教训**：**启动服务前后都 `ps aux | grep` 确认**；端口被占时新进程会 `Address already in use` 静默退出，老进程用旧代码服务请求——表现为"改了代码没生效"

## 9. `"proxy": false` NameError

- **症状**：新进程秒退 `NameError: name 'false' is not defined`
- **根因**：用 `json.dumps` 生成 Python 源码，布尔值是 JS 字面量
- **修复**：`"proxy": false` → `"proxy": False`
- **教训**：程序生成代码后必须 `ast.parse` 校验 + 实际启动验证

## 10. 测速方法错误的乌龙

- **症状**：第一轮测速全部 0.00 MB/s，但电视明明播出了画面
- **根因**：对 m3u8（348 字节文本）测"下载速度"当然约等于 0
- **正确方法**：先拉 m3u8 → 解析出 ts 分片 URL → 对分片测速（本案实测河北源 13-19MB/s）

## 11. 闪剧 APK 解析（未走通的路）

- 用户给的 APK 是 Capacitor 套壳（WebView），assets 无前端 dist（远程加载）
- dex 字符串提取全是广告 SDK（穿山甲/快手），无业务服务器地址
- `na.czl` 是 XOR 混淆配置（key 0x32，内容含 /dev/qemu_pipe 模拟器检测）
- **结论**：此类 App 业务地址运行时下发，离线静态分析拿不到，放弃

## 12. 乐播对带 query 参数的 URL 拒绝换源（HTTP 500）

- **症状**：遥控器切台后电视一直播旧内容（测试卡）；`/api/status` 却显示 PLAYING
- **排查路径**：`GetMediaInfo` 发现电视 CurrentURI 还是旧流 → 手工发 SetAVTransportURI 对照实验：
  - `https://event.pull.hebtv.com/jishi/cp2.m3u8`（无 query）→ 200 接受
  - `http://112.123.243.37:50085/tsfile/live/0015_1.m3u8?key=txiptv&...`（带 query）→ **500**
  - 同一 URL 剥掉 query → **200 接受**，且源本身无 query 也能正常拉流
- **根因**：乐播 DLNA 的 SetAVTransportURI 对 URL 里 `?key=...&...` 这类查询参数处理有缺陷，直接 500 拒绝
- **修复**：`TV.play_url` 在 Set 非 200 且 URL 含 `?` 时自动剥 query 重试一次
- **教训**：SOAP 返回 200 ≠ 换源成功；`soap()` 失败时返回错误字符串而非 int，把 500 全吞了（对比 `r_set==200` 永远 False），排错先看原始状态码

## 13. PLAYING 状态不代表播的是新 URL

- **症状**：换源后 `GetTransportInfo` 一直报 PLAYING，代码判定"直连成功"，电视实际还在放旧流
- **根因**：电视拒绝/未执行新 Set 时**保持旧流继续播**，状态轮询只看 PLAYING 就被旧流骗过
- **修复**：`_play_sync` 改为 `GetMediaInfo` 核对 `CurrentURI` 与下发 URL 一致 + PLAYING 才算直连成功；失败则按优先级轮询频道其余源，全败才转 Mac 中转
- **教训**：DLNA 状态机要"URI+状态"双确认；单确认在"电视自作主张续播旧流"面前必然误判

## 14. 不明 ffmpeg 进程要先查归属（坑 8 补充）

- **症状**：`ps` 里有两个与 tv.py 无关的 ffmpeg 白跑 1080p 转码，输出路径是 `~/.hermes/cache/scratch/hls/`（其他会话的实验残留，PPID=1 孤儿）
- **教训**：排错时先看 ffmpeg 的**输出路径和 PPID** 再认定归属，别把别人的进程算到自己头上；本项目自己产生的 ffmpeg 输出必在 `hls_cache/`
- **附带**：`pkill -9 -f tv.py` 只杀 Python，若真有它 Popen 的 ffmpeg 会变孤儿（PPID=1），重启脚本补 `pkill -9 -f "ffmpeg.*hls_cache"`

## 15. stdout 是管道时日志全丢

- **症状**：想回看"[直连失败]"历史决策，发现进程 stdout 接在已关闭的会话管道上，print 全部丢失
- **修复**：`main()` 里用 `_Tee` 把 stdout/stderr 同时写终端和 `server.log`（行缓冲），排错先 `tail server.log`
- **教训**：常驻服务的日志必须落盘，不能依赖启动它的会话活着

## 16. Relay.start 持锁调用 stop() 自死锁（12:42 事件真凶）

- **症状**：`hls_cache/ch0/` 空、`ff_0.log` 0 字节、无 ffmpeg 进程；`/api/status` 永远停在最后一次成功换台的乐观状态（mode/src 都是 play() 里的预写值），之后所有换台请求无响应
- **排查路径**：给验证脚本挂 `faulthandler.dump_traceback_later` 拿到精确栈——`start` 第 226 行 → `stop` 第 190 行，卡在锁获取
- **根因**：`start()` 在 `with self.lock:` 块内调用 `self.stop()`，而 `stop()` 也要 `with self.lock:`——`threading.Lock` 不可重入，同线程二次获取必死锁。ffmpeg 的 Popen 在锁内、死锁点之后，根本没执行
- **修复**：`self.stop()` 挪到 `with self.lock:` 之前
- **教训**：①不可重入锁的方法互调=自死锁，兜底路径的方法组合要单独跑一遍；②"文件已建但进程未起"= 死在 Popen 之前，沿代码顺序逐行对账；③`/api/status` 的 mode/src 是 play() 预写的乐观值，不是确认值
