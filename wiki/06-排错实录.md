# 06 - 排错实录（bug 全记录）

按发现顺序记录，每条含症状→根因→修复。都是真实踩过的坑。

## 1. mpegts 推流 30 秒后电视自停

- **症状**：直推 mpegts 裸流，电视播 30 秒进入 PAUSED_PLAYBACK
- **根因**：乐播把 ts 当静态文件下载，拉完缓冲区即认为"文件结束"
- **修复**：改推 HLS——ffmpeg 切片 + `omit_endlist`（直播语义），电视无限刷新播放列表

## 2. ffmpeg https 源报 certificate verify failed

- **症状**：curl 拉同 URL 正常，ffmpeg 报 `error:0A000086:SSL routines::certificate verify failed`
- **根因**：自编译 ffmpeg 无系统 CA bundle
- **尝试失败**：`-tls_verify 0` → "Option not found"（不是输入选项，ffmpeg 直接退出）
- **修复**：国内源改用 http 明文（80 端口普遍开放）
- **2026-10 更新**：ffmpeg 改用系统 PATH 的 brew 版（自带 CA bundle）后，https 源可直接拉，本坑仅影响旧自编译版；`-timeout` 选项两版均支持

## 3. ffmpeg 输出文件已存在导致挂死

- **症状**：`File 'tv_buf.ts' already exists. Overwrite? [y/N] Not overwriting - exiting`
- **修复**：命令固定加 `-y`

## 4. Popen 管道写 HTTP 响应 0 字节

- **症状**：`subprocess.Popen(cmd, stdout=self.wfile)` 客户端收到 Content-Type 但 0 数据
- **根因**：组合问题（当时 `-tls_verify` 也在命令里导致 ffmpeg 秒退）
- **修复**：stderr 落日志文件排查出真实报错后逐项解决

## 5. 「Remote end closed connection without response」

- **症状**：Stop/Set/Play 偶发此错误
- **根因**：电视 SOAP 服务并发处理弱，前一个请求没结束又来新的
- **修复**：调用间 sleep；查询加 3 次重试

## 6. state 永远 UNKNOWN（最大坑）

- **症状**：播放正常，但 /api/status 的 state 一直是 UNKNOWN；手工跑同样代码却正常
- **排查路径**：
  1. 怀疑代理干扰 → 检查进程环境变量，干净，排除
  2. 怀疑并发限流 → 加重试，无效
  3. 怀疑 SSDP 地址错 → 对比正常
  4. **加临时 /api/debug 端点返回 SOAP 原始响应** → `nonnumeric port: 'AVTransport_control'` 破案
- **根因**：URLBase 拼接 controlURL 时没补斜杠，`http://x:49152_urn:...` 端口部分变成 `49152_urn`
- **修复**：`controlURL.startswith("/") ? 直接拼 : 补 "/"`
- **教训**：被吞掉的异常要用原始响应暴露，光看返回码不够

## 7. 兜底线程 UnboundLocalError

- **症状**：`UnboundLocalError: local variable 'st' referenced before assignment`（后台线程堆栈）
- **根因**：直连 SOAP 本身失败（非 200）时跳过整个 if 块，`st` 未定义就被日志引用
- **修复**：`st = None` 提到 if 之前
- **教训**：兜底路径恰恰在异常场景触发，其自身代码要最健壮

## 8. 旧进程杀不干净（两次！）

- **症状 A**：`kill 17836` 后 5555 监控循环还在跑 → zsh wrapper 拉起了循环体
- **症状 B**：`pkill -f "python3 tv.py"` 无效 → Xcode Python 进程命令行是 `Python tv.py`（大小写/路径不同）
- **修复**：`pkill -9 -f "tv.py"`（宽松匹配）+ `lsof -ti :8899 | xargs kill -9`（按端口兜底）
- **教训**：**启动服务前后都 `ps aux | grep` 确认**；端口被占时新进程会 `Address already in use` 静默退出，老进程用旧代码服务请求——表现为"改了代码没生效"

## 9. `"proxy": false` NameError

- **症状**：新进程秒退 `NameError: name 'false' is not defined`
- **根因**：用 `json.dumps` 生成 Python 源码，布尔值是 JS 字面量
- **修复**：`"proxy": false` → `"proxy": False`
- **教训**：程序生成代码后必须 `ast.parse` 校验 + 实际启动验证

## 10. 测速方法错误的乌龙

- **症状**：第一轮测速全部 0.00 MB/s，但电视明明播出了画面
- **根因**：对 m3u8（348 字节文本）测"下载速度"当然约等于 0
- **正确方法**：先拉 m3u8 → 解析出 ts 分片 URL → 对分片测速（本案实测河北源 13-19MB/s）

## 11. 闪剧 APK 解析（未走通的路）

- 用户给的 APK 是 Capacitor 套壳（WebView），assets 无前端 dist（远程加载）
- dex 字符串提取全是广告 SDK（穿山甲/快手），无业务服务器地址
- `na.czl` 是 XOR 混淆配置（key 0x32，内容含 /dev/qemu_pipe 模拟器检测）
- **结论**：此类 App 业务地址运行时下发，离线静态分析拿不到，放弃

## 12. 乐播对带 query 参数的 URL 拒绝换源（HTTP 500）

- **症状**：遥控器切台后电视一直播旧内容（测试卡）；`/api/status` 却显示 PLAYING
- **排查路径**：`GetMediaInfo` 发现电视 CurrentURI 还是旧流 → 手工发 SetAVTransportURI 对照实验：
  - `https://event.pull.hebtv.com/jishi/cp2.m3u8`（无 query）→ 200 接受
  - `http://112.123.243.37:50085/tsfile/live/0015_1.m3u8?key=txiptv&...`（带 query）→ **500**
  - 同一 URL 剥掉 query → **200 接受**，且源本身无 query 也能正常拉流
- **根因**：乐播 DLNA 的 SetAVTransportURI 对 URL 里 `?key=...&...` 这类查询参数处理有缺陷，直接 500 拒绝
- **修复**：`TV.play_url` 在 Set 非 200 且 URL 含 `?` 时自动剥 query 重试一次
- **教训**：SOAP 返回 200 ≠ 换源成功；`soap()` 失败时返回错误字符串而非 int，把 500 全吞了（对比 `r_set==200` 永远 False），排错先看原始状态码

## 13. PLAYING 状态不代表播的是新 URL

- **症状**：换源后 `GetTransportInfo` 一直报 PLAYING，代码判定"直连成功"，电视实际还在放旧流
- **根因**：电视拒绝/未执行新 Set 时**保持旧流继续播**，状态轮询只看 PLAYING 就被旧流骗过
- **修复**：`_play_sync` 改为 `GetMediaInfo` 核对 `CurrentURI` 与下发 URL 一致 + PLAYING 才算直连成功；失败则按优先级轮询频道其余源，全败才转 Mac 中转
- **教训**：DLNA 状态机要"URI+状态"双确认；单确认在"电视自作主张续播旧流"面前必然误判

## 14. 不明 ffmpeg 进程要先查归属（坑 8 补充）

- **症状**：`ps` 里有两个与 tv.py 无关的 ffmpeg 白跑 1080p 转码，输出路径是 `~/.hermes/cache/scratch/hls/`（其他会话的实验残留，PPID=1 孤儿）
- **教训**：排错时先看 ffmpeg 的**输出路径和 PPID** 再认定归属，别把别人的进程算到自己头上；本项目自己产生的 ffmpeg 输出必在 `hls_cache/`
- **附带**：`pkill -9 -f tv.py` 只杀 Python，若真有它 Popen 的 ffmpeg 会变孤儿（PPID=1），重启脚本补 `pkill -9 -f "ffmpeg.*hls_cache"`

## 15. stdout 是管道时日志全丢

- **症状**：想回看"[直连失败]"历史决策，发现进程 stdout 接在已关闭的会话管道上，print 全部丢失
- **修复**：`main()` 里用 `_Tee` 把 stdout/stderr 同时写终端和 `server.log`（行缓冲），排错先 `tail server.log`
- **教训**：常驻服务的日志必须落盘，不能依赖启动它的会话活着

## 16. Relay.start 持锁调用 stop() 自死锁（12:42 事件真凶）

- **症状**：`hls_cache/ch0/` 空、`ff_0.log` 0 字节、无 ffmpeg 进程；`/api/status` 永远停在最后一次成功换台的乐观状态（mode/src 都是 play() 里的预写值），之后所有换台请求无响应
- **排查路径**：给验证脚本挂 `faulthandler.dump_traceback_later` 拿到精确栈——`start` 第 226 行 → `stop` 第 190 行，卡在锁获取
- **根因**：`start()` 在 `with self.lock:` 块内调用 `self.stop()`，而 `stop()` 也要 `with self.lock:`——`threading.Lock` 不可重入，同线程二次获取必死锁。ffmpeg 的 Popen 在锁内、死锁点之后，根本没执行
- **修复**：`self.stop()` 挪到 `with self.lock:` 之前
- **教训**：①不可重入锁的方法互调=自死锁，兜底路径的方法组合要单独跑一遍；②"文件已建但进程未起"= 死在 Popen 之前，沿代码顺序逐行对账；③`/api/status` 的 mode/src 是 play() 预写的乐观值，不是确认值

## 17. 进程级 no_proxy='*' 会让 curl/urllib 连显式代理也绕过

- **症状**：「拉源」功能三个 GitHub 列表全部拉取失败；同样的 curl 命令在 shell 里手工执行却成功
- **排查路径**：curl 直连/代理对照 → `no_proxy='*' curl -x 代理 ...` 复现失败 → 定位到服务进程 `main()` 为保护 DLNA 设置了 `os.environ["no_proxy"] = "*"`
- **根因**：curl 和 urllib 的代理处理器都会咨询 no_proxy 环境变量，`*` 匹配所有主机——**连显式指定的 `-x`/ProxyHandler 也被绕过**；子进程还会继承这套环境变量
- **修复**：给 curl 子进程传清洗后的环境（pop 掉 no_proxy/NO_PROXY）
- **教训**：`no_proxy=*` 是进程级"核开关"，设了它之后任何需要代理的出站请求（拉 GitHub 列表）都得绕开这套环境；DLNA 保护和外网拉取是互相冲突的需求，只能按请求区分处理

## 18. 内嵌 JS 的全角标点会炸掉整个页面脚本

- **症状**：遥控器页面某次更新后全部交互失效
- **根因**：Python 字符串里写 JS 时混入全角冒号 `：`（应为 `:`），肉眼极难发现；一处语法错误使整个 `<script>` 不执行
- **修复**：把页面 JS 提取出来跑 `node --check` 做语法校验
- **教训**：Python 文件里嵌 JS 无法靠 `ast.parse` 兜底，每次改 PAGE 后必须跑一次 `node --check`；输入法切换是这类错误的常见来源

## 19. 源画质会随时间波动，单次分辨率探测不可靠

- **症状**：河南卫视某源上午探测为 1920×1080 并按高清排到线路 1，下午复测同一 URL 变成 720×576 标清（用户看到黑边）
- **根因**：IPTV 聚合源会随节目/时段切换转码档位，"这条源是高清"不是恒定属性
- **修复**：把已知波动源按最近一次实测结果重排（183.10 稳定 1080p 排前）；「拉源」合并的高清候选同样依赖探测时刻
- **教训**：分辨率要按"最近实测"理解，重要频道留一条以上高清候选；想全自动就定期跑分辨率重排（维护脚本思路见 wiki/07）

## 20. 保存接口参数名大小写不一致导致校验恒失败

- **症状**：`/api/settings/save` 传参正确却总报"电视 IP 格式不对"
- **根因**：构造参数字典用了大写的 `DEFAULTS` 键（TV_IP）去取小写的 query 参数（tv_ip），全部取到空串
- **修复**：参数名单独显式列出：`{k: qs.get(k, [""])[0] for k in ("tv_ip", "mac_ip", "proxy", "ffmpeg")}`
- **教训**：HTTP 入参名与内部常量名不要靠"恰好同形"关联，集中定义一份参数名清单；表单类接口写完必须打一遍真实请求

## 21. 坑12 真根因：SOAP 体里的 URL 没做 XML 转义（审查修正）

- **症状**：同坑12——带 query 的源 SetAVTransportURI 必 500，只能剥 query 重试兜底；token 型源剥了 query 反而拉不到流
- **根因**：`<CurrentURI>{url}</CurrentURI>` 原样拼接，直播源 query 里大量 `&token=...`（115/255 条），裸 `&` 不是合法 XML 实体，电视解析器必然拒收——"带 query 必 500、剥掉就 200"与 XML 良构性完全吻合，坑12 归咎的"乐播缺陷"至少是共因
- **修复**：下发前 `xml.sax.saxutils.escape(url)`；`current_uri()` 对 GetMediaInfo 返回值 `unescape` 后再与下发 URL 比对（否则 `&amp;` 永远对不上）；剥 query 重试保留为二级兜底
- **教训**：XML/SOAP 里拼外部字符串先转义，这是协议级正确修复；"试出来能绕过去"的 workaround 要回头追一层根因

## 22. 审查加固批次（2026-10-13，随坑21 一起修）

一次性修掉的隐患，按主题归档：

- **channels.json 并发写损坏**：「刷新源」「拉源」可并行，两个 `json.dump` 各自 `open(...,"w")` 截断后交叉写 → 损坏 JSON。修：`CH_LOCK`(RLock) 包住变异+写盘，临时文件 + `os.replace` 原子写
- **SOAP 并发打电视**（坑5 的衍生）：`/api/status` 每 2.5s 轮询与 `_try_direct` 确认循环同时打 SOAP，偶发断连让直连误判失败。修：`TV.soap_lock` 串行化所有请求，查询类超时降 4s
- **SIGTERM 不杀 ffmpeg 孤儿**（坑14 的根治）：`pkill` 发 SIGTERM 时主进程直接死，ffmpeg 继续转码。修：注册 SIGTERM handler，先 `relay.stop()` 再退出（不抢 Player.lock，避免被换台线程堵几十秒）
- **换台线程堆积**：连点 N 个台会排队把每个都播一遍。修：`Player.gen` 世代号，旧请求发现过期即作废
- **mode 永远停在 starting**：中转全失败只打日志不改状态。修：置 `mode="error"`（页面显示"失败"）
- **alive_check 无视 proxy 标记 / ffmpeg 环境被 no_proxy 架空**（坑17 同款，主角换成 ffmpeg 与 urllib）：修：按源 `proxy` 标志走清洗环境的 curl；`use_proxy` 时 pop 掉 no_proxy 再传 ffmpeg
- **测活线程爆炸**：255 条源起 255 个线程。修：`parallel_map` 固定 worker 池（worker 数=并发上限）
- **其他**：errlog 句柄泄漏（Popen 后关父进程副本）；`hls_cache/` 旧频道目录只增不减（换台时清）；远端频道名进 `innerHTML` 的 XSS（`esc()`）；`do_GET` 异常裸断连接（统一 500 JSON）；server.log 超 5MB 轮转；IP 校验用 `ipaddress`（原正则放过 999.1.1.1）
- **教训**：单文件脚本的"能跑"和"可长期跑"之间差一整批并发/资源/转义问题；兜底路径（坑7 老调）和外部数据入界处（XML/HTML/JSON）要重点审

## 23. play() 在 t.start() 之后写乐观状态，被播放线程终态覆盖（竞态）

- **症状**：单测偶发（后转为必现）`mode` 停在 `starting`：线程日志显示已走到 `[中转全失败]`（`mode="error"` 赋值之后的打印），主线程读 `pl.mode` 却是 `starting`
- **排查路径**：`__setattr__` 追踪 + `faulthandler.dump_traceback()` 定位 → 给 tv.py 打插桩补丁打印 `id(self)` → 真相是**两条写入的顺序**：`_play_sync(): mode=error` 在缓冲输出里排在 `play(): mode=starting` **前面**
- **根因**：`play()` 把 `self.mode="starting"` 等乐观状态写在 `t.start()` **之后**。GIL 可能在 `start()` 处切到播放线程；电视拒连快 + ffmpeg 秒退时线程瞬间跑完写好 `error/direct/relay`，主线程恢复后照样执行 `mode="starting"` 把终态覆盖掉。生产中播放动辄数秒所以极少触发，但只要全链路失败够快（电视不在线 + 源地址非法）就可能发生
- **修复**：乐观状态（current/cur_src/mode）全部移到 `t.start()` **之前**写；单测加 20 连发压力子测试防回归
- **教训**：①"先启动线程再收尾主线程状态"是经典竞态形态，`Thread.start()` 之后不该再写会被线程写的同一份状态；②排查时给两个角色都打上 `id()` 和顺序戳，比读日志靠谱；③两个观测陷阱浪费了大量时间——`faulthandler` 直接写 fd 而 `print` 是块缓冲，管道/文件里看到的"顺序"是假的（dump 其实出现在输出最顶部）；`ps aux|grep` 会匹配到自己命令里的 echo 字符串（坑14 的轻量复发，数 ffmpeg 用 `pgrep` 按进程名匹配）
## 24. SSDP 被宿主防火墙拦掉 + 乐播端口漂移 → 所有频道无法播放（2026-10-13 线上故障）

- **症状**：遥控器每个台都播不出来，日志清一色 `Set/Play 失败 set=0 play=0`（所有源、所有频道），
  `state` 永远 `UNKNOWN`；`/api/status` 显示 `mode=relay/error`，中转也全失败
- **误判方向**：一开始怀疑是当天的代码改动（坑21~23 那批审查加固）改坏了。**实际与改动无关**——
  `find_tv`/`guess_tv_ctrl`/SSDP 那段在两个版本里逐字节相同，且旧版本（d0ae490，17:41 部署）
  在 17:41:58 还正常播放过，18:12:19 才开始全线失败
- **真根因（两条叠加）**：
  1. **电视换端口**：乐播 DLNA 端口不是固定的，电视/投屏应用重启后从 `49152` 变成 `49153`
     （`description.xml` 的 `<URLBase>` 会如实写出真实端口）。`set=0 play=0` 是 `urlopen` 抛异常
     被 `soap_raw` 吞成 0 的特征码——**连接被拒**，不是电视拒绝播放
  2. **SSDP 拿不到回包**：服务器上 firewalld 把电视发往本机**临时端口**的 SSDP 应答 REJECT 了
     （`filter_IN_public_REJECT ... SRC=<电视IP> DPT=43158`；`--add-service=ssdp` 也无效，
     因为被拦的是回包的目标端口而非 1900），于是 `find_tv()` 返回 `None`，只能走死猜 `49152` 的兜底——
     正好猜在已失效的旧端口上
- **为什么本地 Mac 复现不出来**：Mac 没开防火墙，SSDP 正常应答 → `find_tv()` 拿到 49153 → 一切正常。
  同一份代码、同一个电视，两台机器结果相反，差别只在防火墙
- **修复（2026-10-13 追加 A+B 两层根治）**：
  1. **A. 宿主防火墙放行电视 UDP 回包（根治 SSDP 失联）**：`firewalld` 默认 REJECT 电视发往本机临时端口的 SSDP 应答。放行后 SSDP 立刻恢复 30 条应答、`find_tv()` 直接拿到真实端口与设备名"客厅电视"。
     ```bash
     firewall-cmd --permanent --zone=public \
       --add-rich-rule='rule family="ipv4" source address="<电视IP>" protocol value="udp" accept'
     firewall-cmd --reload
     ```
     **注意语法**：`protocol value="udp"` 才对，写成 `protocol="udp"` 会报 `INVALID_RULE`（且静默不生效）。
     另：`--add-service=ssdp`（只放行 1900/udp）**无效**——被 REJECT 的是回包的**目标端口**（如 `DPT=43158`），不是 1900。
  2. **B. HiSmart 38400 提为主力控制端点**：电视固件自带的 HiSmart renderer 端口固定，不像乐播那样重启漂移，所以 `discover_tv_ctrl()` 的顺序改为
     **HiSmart(38400) > SSDP > 乐播(4915x)**（SSDP 仍在，用于拿友好设备名，并作为 HiSmart 不可用时的次选）。
- **三条代码防线**（保留，作为 A/B 之外的最后保险）：
  1. `soap_probe()`：任何候选端点都用 `GetTransportInfo` 验活。**"拿到地址"不等于"地址活着"**；
     还要求响应体含 `GetTransportInfoResponse`/`CurrentTransportState`，防"端口通但非 DLNA"（同机 HTTP 服务撞端口）
  2. `discover_tv_ctrl()`：SSDP 结果**先验活**，不可用则并行探测候选端口
     （乐播 49150~49160 + 海信 HiSmart `38400/upnp/control/mingusavtr`），命中即用
  3. `TV._maybe_rediscover()`：运行中连续 3 次传输层失败 → 自动重发现并热切换（10s 冷却）。
     只调模块级 `soap_probe`，不碰 `soap_lock`/`soap_raw`，避免坑16 那种自死锁
- **实测**：修复后服务器与本地 Mac 均 `mode=direct state=PLAYING`；电视两个渲染端点
  （乐播 49153 与 HiSmart 38400）`Set=200 Play=200` 都能投屏，互为兜底
- **能力等价性实测（决定 B 敢不敢上主力）**：把两个 renderer 都指向本机 18999 探针服务，**电视都真的回拉了 `/probe.m3u8` + `/seg1.ts`**（`state` 与 `CurrentURI` 双条件确认）——证明不是只报 PLAYING 的假象；`GetMediaInfo`/`GetTransportInfo`/`Set`/`Play` 全部 200，换台后 `CurrentURI` 比对一致；中转路径下电视同样回拉了 `/hls/chN/live.m3u8` + `seg00000.ts`。
  注：`RelTime` 恒为 `00:00:00`（两个 renderer 都一样），**不能用它判断是否真在播**——直播流下乐播与 HiSmart 都不更新该字段。
- **教训**：
  - ①**"所有源同时失败"先怀疑控制通道，别查源**——源头失效不会如此整齐地全体阵亡
  - ②`set=0`（异常吞成 0）与 `set=500`（电视明确拒绝）是两类问题，排查第一步先把它们分开
  - ③**死猜端口就是定时炸弹**：任何"先试默认端口"的兜底都必须带验活与重发现，否则电视一重启就全盘失效
  - ④排查"是不是某次提交改坏的"最快路径是 `git diff <commit> -- <file>` 看**是否真的碰到相关代码**，
    再用**同一份代码在两台机器跑**（Mac 正常 / 服务器失败）即可证明是环境而非代码
